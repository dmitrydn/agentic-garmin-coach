# Спека: проактивный слой мониторинга

> **Статус**: дизайн, код НЕ трогается. На ревью Дмитрию. Составлено 2026-07-09.
> **Проблема** (диагноз по коду): триггеры торможения все автономные/TSS-based
> (HRV-отклонение, RHR-тренд, ACWR из CTL/ATL, volume_status по минутам, spacing
> качества, 80/20). Инсерционная тендинопатия ахилла 08.07 пришла от механической
> вертикальной перегрузки (набор ×3.5 за неделю), которая **не даёт автономного
> сигнала** — HRV/RHR были чистые, ACWR «формально оптимальным». Система слепа
> к вектору, который травмировал. Плюс нет детектора перерасхода дозы по сессии,
> и отклонения от плана систематически легитимизировались переписыванием таргетов
> вверх (v2.5: «атлет расширил сессию до 3.5ч» → таргеты пересчитаны под факт).
> **Цель слоя**: сделать механическую нагрузку и перерасход дозы первоклассными
> отслеживаемыми величинами, и тормозить/взбодрять проактивно, ДО факта срыва.

## 1. Недельный монитор вертикали + детектор скачка `[приоритет 1]`

**Зачем**: ловит ровно причину травмы 08.07. Самый высокий ROI, данные есть.

**Новая функция** (metrics.py, рядом с `weekly_volume_status`):
```
def weekly_vertical_status(
    actual_vert_m: float | None,
    target_vert_m: float | None,
    prev_week_vert_m: float | None,
    tolerance: float = 0.15,
    spike_threshold: float = 0.35,
) -> dict:
    # returns {"vert_status": over|under|on_track|unknown,
    #          "vert_pct": ±%,
    #          "vert_spike": bool, "vert_wow_pct": ±%}
```
- `actual_vert_m` = SUM(elevation_gain_m) за текущую неделю Пн-Вс (тот же оконный
  хелпер, что для минут).
- `prev_week_vert_m` = та же сумма за прошлую Пн-Вс → week-over-week.
- `vert_spike=True` при росте >`spike_threshold` (35%) неделя-к-неделе.

**Флаги** (context_agent, там же где volume_over): `vert_over:{pct}`,
`vert_under:{pct}`, `vert_spike:{wow_pct}`.

**Порог**: на неделе 02–08.07 набор 250→868 м = +247% w/w → `vert_spike` сработал бы
с огромным запасом. `spike_threshold=0.35` — консервативно; калибровать по бэктесту (§6).

**Интеграция в граф**: metrics_agent считает → context_agent добавляет флаг →
coach_agent (Opus) видит в промпте → synthesis выносит в Telegram при наличии.

## 2. Детектор перерасхода дозы по сессии `[приоритет 1]`

**Зачем**: ловит «40 мин непрерывного Z3 вместо 12 мин интервалов» (01.07) и
самовольное расширение длинной (08.07) — в момент, а не постфактум.

**Проблема парсинга**: точная плановая доза интенсивности («4x3 мин Z3» = 12 мин Z3)
лежит в free-text `description`. NLP по описанию — хрупко. **Рекомендация**: добавить
в конфиг плана структурные дневные таргеты (маленькое расширение схемы, не ломает
koop_plan_agent — новые опциональные ключи):
```
wed: {type: quality, duration_min: 65, target_load: 75, target_vert_m: 640,
      hi_intensity_min: 12, zones: [...], description: "..."}
```
Тогда сравнение — чистая арифметика, без разбора текста.

**Новая функция** (metrics.py):
```
def session_overshoot(actual: dict, planned: dict,
                      dur_tol=0.25, load_tol=0.30, vert_tol=0.30, hi_tol=0.50) -> dict:
    # actual: строка activity_cache за дату плана
    # planned: koop entry (+ структурные таргеты из §2)
    # returns {"overshoot": bool, "dims": [...], "ratios": {...}}
```
- Флаг `session_overshoot`, если любое из: длительность >125% плана, load >130%,
  vert >130%, hi_intensity_min >150%.
- Сопоставление факт↔план по дате (вчерашняя сессия vs вчерашний koop entry).

**Флаг**: `session_overshoot:{dims}` (напр. `session_overshoot:hi_intensity+load`).

**Интеграция**: новый маленький шаг после data/metrics (или внутри context_agent),
берёт вчерашнюю activity_cache строку + `entry_for_date(config, вчера)`.

## 3. Механический ACWR (вертикаль) `[приоритет 2]`

**Зачем**: отдельный вектор торможения, невидимый для TSS-ACWR. Прямой фикс слепого
пятна на уровне тренда, а не одной недели.

**Новая функция** (metrics.py, рядом с `calculate_acwr`):
```
def mechanical_acwr(daily_vert: list[tuple[date, float]]) -> dict:
    # acute = сумма D+ за 7 дней; chronic = средненедельный D+ за 28 дней (EWMA)
    # returns {"mech_acwr": ratio, "mech_acwr_zone": low|optimal|caution|high}
```
- Пороги по Gabbett: >1.5 high, 1.3–1.5 caution, <0.8 low (аналогично TSS-ACWR).
- Данные: `elevation_gain_m` по дням за 28 дней — в БД есть.

**Флаг**: `mech_acwr_high:{ratio}` / `mech_acwr_caution:{ratio}`.

**Ограничение (честно)**: чистая вертикаль — прокси. Настоящая механическая/сухожильная
нагрузка зависит ещё от эксцентрики спусков, темпа, массы. v1 = ACWR по метрам набора;
v2 может добавить downhill-эксцентрику, если появится сигнал спусков.

## 4. Еженедельный авто-обзор траектории `[приоритет 2]`

**Зачем**: та самая «месячная линза», что сработала по запросу — но по расписанию и
проактивно. Плюс форвард-взгляд: хватает ли подготовки под цель (твой запрос «взбодрять
если недобор»), а не только «тормозить при переборе».

**Механизм** (2 варианта):
- (a) Расширить `memory_agent` (он и так еженедельно переписывает ATHLETE_MEMORY) —
  добавить секцию «trajectory review».
- (b) Отдельный read-only `trajectory_agent` (Sonnet), пишет в `trajectory.log` +
  опционально Telegram. **Рекомендую (b)** — разделение ответственности, не мешает памяти.

**Считает** (детерминированно, Python; LLM только на формулировку вывода):
- по-недельно: км, D+, load, кол-во quality, ACWR, mech_ACWR за 4–6 недель;
- дрейф: тренд объёма/вертикали vs план;
- паттерн перебора: счётчик `session_overshoot` за период (см. §5);
- **форвард**: прогрессия длинных и суммарная вертикальная экспозиция vs то, что
  требует 90k/2500м D+ → флаг недо/пере-подготовки.

**Расписание**: воскресенье вечером (конец недели Пн-Вс). Можно через уже
существующий scheduled-task механизм.

## 5. Override-guard `[приоритет 3, часть-workflow]`

**Зачем**: тормоз, который ты переписываешь под импульс — не тормоз. Отклонение должно
быть помечено ДО того, как таргеты пересчитают под факт.

**Код-часть**:
- Детектор поднятия таргетов: version-diff `weekly_targets[block]` между версиями плана
  (плановые правки — ручной md-edit; хранить снапшот таргетов в pipeline_meta, сравнивать).
  Если target_minutes/tss/vert подняты внутри активного блока → флаг `targets_raised_midblock`.
- Счётчик перебора: агрегировать `session_overshoot` (§2) в скользящий tally в
  pipeline_meta → coach видит «3-й перебор за 2 недели», паттерн становится явным.

**Флаг**: `override_pattern:{n_overshoots}/{window}`, `targets_raised_midblock`.

**Workflow-часть (не код, дисциплина)**: coach_agent при `targets_raised_midblock`
формулирует прямой вопрос — «таргеты подняты под факт превышения: это осознанное
решение или подгонка под перебор?» — и требует явного подтверждения, а не молчит.

## 6. Верификация (как докажем, что работает — до мержа)

**Главный тест — бэктест на двух известных инцидентах.** Триггер бесполезен, если бы
не сработал на реальной травме. Прогнать каждую новую метрику на исторических данных
из coach.db:

| Инцидент | Что должно сработать | Ожидаемо |
|---|---|---|
| 08.07 ахилл (набор ×3.5, HRV/RHR чистые) | `vert_spike`, `mech_acwr` растёт | vert w/w +247% → флаг с запасом; TSS-ACWR молчал бы (подтверждает слепое пятно) |
| 01.07 (2×20 Z3 вместо 4×3) | `session_overshoot:hi_intensity+load` | duration Z3 40 vs 12 мин, load 104 vs план |
| 20–21.06 (ATL 105, HRV 37→20) | существующие HRV/ACWR флаги | контроль: старые триггеры на автономном срыве работают — новые их не ломают |

Скрипт бэктеста: `tools/backtest_triggers.py` — читает историю из coach.db, гоняет
новые функции по датам, проверяет что флаги поднялись на инцидентах и НЕ поднимались
на спокойных неделях (ложные срабатывания).

**Юнит-тесты по слоям** (обязательно, Verification Protocol в CLAUDE.md):

| Слой | Файл | Новые тесты |
|---|---|---|
| I (математика) | test_metrics.py | `weekly_vertical_status` пороги; `session_overshoot` рейши; `mechanical_acwr` окна/зоны |
| I (флаги) | test_context_agent.py | vert_spike/vert_over/session_overshoot/mech_acwr_high попадают в context_flags |
| B (бизнес-гарантии) | test_business_scenarios.py | `vert_spike ×3.5 → vert_spike flag present`; `session Z3 40>12мин → session_overshoot`; `mech_acwr>1.5 → flag` (по образцу `test_acwr_high_risk_flag_always_present`) |
| Контракт | test_contracts.py | схема вывода trajectory_agent (§4) |

**Калибровка порогов**: 35% spike, 125%/130% overshoot, 1.5 mech-ACWR — стартовые.
После бэктеста подогнать так, чтобы оба инцидента ловились, а спокойные недели
(напр. recovery 22–28.06) НЕ давали ложных флагов.
